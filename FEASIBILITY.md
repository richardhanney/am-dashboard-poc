# Feasibility and evidence boundaries

This standalone UX prototype uses invented records and its own sanitised, frontend-facing projections. A read-only source review informed the relationships, optional values and evidence boundaries below. No production implementation code was copied. No database or service was queried. The review establishes a plausible source mapping; it does **not** establish deployment, access permissions, evidence completeness or historical retention.

## Scope and consistency

Account status, capacity, health, current inventory/configuration and feed history remain account-wide. Rule-linked device audits have a selected date range but stay account-wide because a defensible historical user join was not established. User-linked activity, trips, briefing audits, check-ins and SOS follow the audience filter. Exports identify their audience and definition.

Health engagement uses current enabled accounts with recorded activity in the fixed latest 90 days divided by current enabled accounts. Healthy means strictly above the chosen threshold. Any selected check failing makes the account unhealthy; manual unhealthy overrides the checks. Missing required evidence or no selected checks means Not assessable when no check fails.

Check-in response rate uses completed requests divided by all requested records in the request-date cohort, including pending and missed requests. Zero requests produces no percentage. Enabled accounts are a current snapshot, never a historical chart series. Commercial 365-day active-user criteria remain to be validated separately.

## What still needs production validation

Authorised reporting endpoints, tenant/group visibility, event semantics, data retention, late corrections, pagination, time zones and consistent exports must be verified against the target runtime and database. Persisted preferences and a reporting cache are future implementation work. No production readiness or billing-grade accuracy is claimed by this static prototype.
